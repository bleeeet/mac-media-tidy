# 媒体整理 · mac-media-tidy

把一个文件夹里的照片和视频一次性整理干净：**去重、HEIC 转 JPG、视频压制、图片瘦身**。
纯本地网页工具，macOS 专用，文件不出本机，不联网、不上传、不需要账号。

> **English** — A local web tool for macOS that tidies up a folder of photos and videos in
> one pass: it removes byte-identical duplicates, converts HEIC to JPG (preserving EXIF and
> timestamps), transcodes oversized videos to H.265 1080p30, and shrinks images over 3MB.
> Everything runs on your own machine — no uploads, no accounts, no network calls. Originals
> are moved to a backup folder by default and are never deleted outright. It keeps a ledger
> of what it has already processed, so running it twice never re-compresses the same file.
> The interface is in Chinese.

![界面截图](docs/screenshot.png)

## 它解决什么问题

手机相册导出到电脑之后，通常是这么一堆东西：同一张照片存了三份、iPhone 拍的 HEIC 在很多软件
里打不开、随手录的 4K60 视频一个就是几个 G。手动一个个处理很烦，用现成的批处理工具又往往
太糙——要么无差别重压一遍（画质越洗越差），要么直接覆盖原文件（出了错没法回头）。

这个工具的取舍是：**宁可少做，不可做错**。

- 已经达标的文件**完全不动**，不会为了"统一格式"重压一遍
- 压完反而更大就**丢弃产物、保留原件**
- 处理过的文件**记在案**，下次运行直接跳过，不会一代代劣化
- 原件默认**移到备份文件夹**而不是删除，每一步都有可回滚的记录
- 扫描阶段**纯只读**，先给你看清单，确认了才动手

## 四件事

| 功能 | 说明 |
|---|---|
| **去重** | 内容完全相同的图片/视频只保留最早的一份 |
| **HEIC → JPG** | 保留 EXIF 与原始修改时间 |
| **视频压制** | 超标视频转 H.265 / 1080p / 30fps / 约 2Mbps |
| **图片瘦身** | 超过 3MB 的图片压到 3MB 以内 |

每一项都能单独开关。

## 环境要求

- **macOS**（图片处理依赖系统自带的 `sips`）
- **Node.js 20+**
- **ffmpeg / ffprobe** —— 只有处理视频才需要：`brew install ffmpeg`

启动时会自动检测，缺什么会在页面顶部提示，不影响用不到的功能。

## 快速开始

```bash
git clone https://github.com/bleeeet/mac-media-tidy.git
cd mac-media-tidy
npm start
```

浏览器打开 <http://127.0.0.1:7788>。没有依赖需要安装——整个项目零 npm 依赖，只用 Node 标准库。

也可以双击项目里的 **`启动媒体整理.command`**：自动起服务并打开浏览器，关掉终端窗口即停止。
想放到顺手的位置就右键「制作替身」，把替身拖到桌面或 Finder 侧边栏。

## 选文件夹的三种方式

浏览器出于安全策略不会把本地绝对路径交给网页，所以给了三条路：

1. **拖进页面** —— 工具拿到文件夹名和几个样本文件后，会在 `~/Downloads`、`~/Desktop`、
   `~/Pictures`、`~/Documents`、`~/Movies` 及其两级子目录里反查。唯一匹配就直接开始，
   多个同名文件夹会列出来让你点选。
2. **粘贴路径** —— Finder 里选中文件夹按 `⌘⌥C` 复制路径，贴进输入框。也认从终端拖进来的
   转义路径。
3. **点「浏览」** —— 内置目录浏览器，从主目录逐级点进去。

选定后先看预演清单，确认无误再点「开始处理」。**文件夹下所有层级的子目录都会一并处理。**

## 安全说明

预演页有一个 **「备份原件到『原图』文件夹」** 开关，默认开启：

- **开启（默认）** —— 被替换和判为重复的原件都移动到目标文件夹下的 `原图/`，并在
  `原图/manifest.json` 里记录每一步操作，可据此手工回滚。确认结果无误后自行删掉 `原图/` 即可。

  如果你的文件夹里**本来就有**一个叫「原图」的文件夹，工具不会往里塞东西——它靠有没有
  `manifest.json` 来分辨归属，是你自己的就另建 `原图-备份/`，你那个照常参与扫描和处理。

- **关闭** —— 原件**直接删除，无法回滚**。同时会把上次留下的备份目录一并清理掉（同样只清理
  带 `manifest.json` 的、确认是本工具建的那些）。只在你确定不需要留底时用。

所有写入都走「临时文件 → 校验 → 原子重命名」，中途中断不会留下半个文件。单个文件出错只记入
错误列表，不影响其余文件继续处理。关掉页面也不影响处理——任务在服务端继续跑，重新打开页面
可以接上进度。

旧版本创建的 `_trash/` 目录仍会被扫描跳过，不必手工清理。

## 不会重复压缩

每次处理成功后，工具把产物记进目标文件夹根部的隐藏文件 `.media-kit.json`（文件名、体积、
修改时间、做了什么）。下次再对同一个文件夹运行时，记录里的文件直接跳过。

这一点对画质很重要：反复有损压缩会一代代劣化。已记录的视频连 `ffprobe` 都省了，重复扫描
大文件夹会明显更快。

判定依据是**体积 + 修改时间**——你在别处改动过这个文件，记录自动失效、重新参与处理。想强制
全部重来，删掉 `.media-kit.json` 即可。

```json
{
  "version": 1,
  "files": {
    "旅行/IMG_0001.jpg": { "size": 1394333, "mtime": 1785567418090, "action": "image-compressed" }
  }
}
```

会被记下的有四种：压缩过的图片、转换过的 HEIC、压制过的视频，以及「压了但产物反而更大、
已丢弃」的文件——最后这种不记的话，每次运行都要白压一遍（视频尤其贵）。去重删掉的文件不记录。

## 处理规则

| 项目 | 规则 |
|---|---|
| 去重判定 | 文件大小分组 + SHA-256 完全一致 |
| 保留哪一份 | 修改时间最早者；时间相同则取路径字典序最小的 |
| 视频体积门槛 | 小于 10MB 的视频一律不压，连 `ffprobe` 都不跑 |
| 视频压缩触发 | 体积 ≥10MB，且（长边 >1920 或 短边 >1080 或 帧率 >30 或 码率 >3Mbps） |
| 视频输出 | `hevc_videotoolbox`，tag `hvc1`，2Mbps，音频 AAC 128k |
| 图片压缩触发 | 体积 >3MB |
| 图片质量档位 | 85 → 75 → 65 → 55，每档均从原图重新编码（不叠加有损压缩） |
| 带透明通道的 PNG | 不转 JPG，改用尺寸档位 4000 → 3000 → 2000 → 1500 逐级缩小 |
| 不处理的格式 | GIF / WebP / BMP 只参与去重，不做转换压缩 |
| 并发 | 视频 4，图片 CPU 核数，哈希 8 |

### 几个需要知道的行为

- **HEIC 转 JPG 后文件会变大**，通常是原来的 1.5–2 倍。HEIC 的压缩效率本就约为 JPEG 的两倍，
  换格式必然涨体积。工具会如实把这部分负收益从"节省空间"里扣掉。只想省空间而不在意格式的话，
  关掉「HEIC 转 JPG」开关即可。转出的 JPG 如果超过 3MB 且开着「图片压缩」，会接着降档直到
  达标（每一档都从原始 HEIC 重新编码，不叠加有损）。
- **小于 10MB 的视频一律不碰**，哪怕它是 4K60。这类文件压完省不下多少空间，却要付出一次转码
  时间和一轮画质损失。想改门槛就动 `lib/video-rules.js` 里的 `MIN_VIDEO_BYTES`。
- **竖屏视频不会被转横**。约束是「短边 ≤1080 且长边 ≤1920」，所以 1080×1920 保持原样，
  2160×3840 会缩成 1080×1920。
- **压完更大就放弃**。视频或图片处理后体积反而增加（且不是必须做的格式转换），工具会丢弃产物、
  保留原件，标记为「已跳过」。
- **已达标的文件完全不动**。1080p30 且码率正常的视频、3MB 以内的图片都原样保留。

## 项目结构

零依赖，只用 Node 标准库 + 系统自带的 `sips` / `ffmpeg`。

```
server.js              HTTP 服务、SSE 进度流、依赖自检
lib/
  scan.js              递归扫描、格式分类、备份目录归属判定
  dedup.js             按体积分组 + SHA-256 比对
  plan.js              只读预演：算出要做什么，不动文件
  runner.js            执行编排、事件发布、记录写入
  image.js             sips 转换与质量/尺寸阶梯
  video.js             ffprobe 探测与 ffmpeg 压制
  video-rules.js       所有阈值常量与触发判定
  ledger.js            .media-kit.json 处理记录
  trash.js             备份目录与 manifest（含不备份模式）
  resolve.js           从文件夹名反查绝对路径
  queue.js             并发队列
  exec.js              子进程封装
public/                前端（原生 JS，无框架、无构建步骤）
```

设计上把「决定做什么」（`plan.js`）和「实际去做」（`runner.js`）分开，所以预演阶段可以保证
纯只读。所有阈值集中在 `video-rules.js`，想改行为基本只用动那一个文件。
